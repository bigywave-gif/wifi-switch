# 版本记录与发布规则

## 参考与本项目约定

参考 [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) 的人工分类记录方式，以及 [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) 的版本含义和已发布制品不可修改原则。这是工程约定，不是法律或强制认证标准。

本项目当前使用 0.y.z 内部开发版本，历史编号保留，不追溯重排。对外稳定接口尚未定义，因此不宣称历史版本严格遵守 SemVer。当前小范围改动继续递增 patch；较大兼容功能批次可递增 minor；未来进入 1.0 后应先定义兼容合同，再按不兼容变更/兼容新增/兼容修复选择 major/minor/patch。Mac 构建号每次新包单独递增。Windows 使用自身产品版本，不能复制 Mac 构建号。

## 每个版本必须写什么

版本记录以使用者可理解的变化为主，不直接粘贴提交日志，也不能只写“优化体验”“修复若干 BUG”。每版记录：

1. 平台、版本、发布日期（Asia/Shanghai，YYYY-MM-DD）和构建号；缺失历史证据明确标注。
2. Added / 新增：新增入口、行为或能力，说明从哪里使用。
3. Changed / 变更：既有功能的行为变化，注明默认值或兼容影响。
4. Fixed / 修复：具体触发场景、原问题与修复后行为。只有已完成的修复放这里，未解决的诊断放验证限制。
5. Removed / 移除、Deprecated / 弃用、Security / 安全：有相应变化才列，不为凑分类写无意义空项。
6. 验证与限制：实际跑过的测试、UI/真实设备验证边界、尚未完成的验收。编译和包校验不等于安装或认证成功。
7. 如涉及存储、系统网络、钥匙串、安装目录或卸载行为，说明升级影响与是否需要用户操作；没有这类变化可简述无需数据迁移。
8. 有独立验证文档时提供相对链接；产物名称与版本一致，校验和由打包脚本生成，不能预填未生成的摘要。

## 发布步骤

- 开发中先写在各平台 CHANGELOG.md 的 Unreleased，完成后整理为顶部的具体版本条目。
- 同时更新应用元数据、README 当前版本及安装文件名；保留已有历史说明和旧制品。
- Mac 运行 `python3 scripts/test-check-release.py`，再运行 `scripts/package-internal.sh`。脚本要求版本/构建递增、当前版本说明与构建一致、有效日期、至少一项实际分类变更及非空验证限制。代码只能检查结构，作者仍须核对事实，禁止复制旧版本说明冒充新变化。
- Mac 包内放 CHANGELOG.md / CHANGELOG.txt，应用资源内放 CHANGELOG.txt。签名后只读挂载核对它们与源文件一致，再记录发布版本。
- Windows 的历史记录本次仅补文档，不更改其构建/安装代码。Windows 下次发布时必须人工更新对应 CHANGELOG 和验证记录；目前没有宣称 Windows 打包脚本已具备相同自动门禁。
- 发布完成后，交付消息同时给出版本、主要新增/修复、验证限制、安装包路径，并明确是否安装到本机。
